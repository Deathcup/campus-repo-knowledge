# 论文总结与实验报告：从 Procedural Skills 到 Strategy Genes

> 论文: Wang, Ren, Zhang. *From Procedural Skills to Strategy Genes: Towards Experience-Driven Test-Time Evolution.* arXiv:2604.15097, 清华大学 × EvoMap, 2026.

## 一、论文说了什么

这篇论文问了一个很根本的问题：**Agent 的经验应该用什么形式存储，才能在推理时真正帮到模型？**

现在的做法是把经验写成 Skill 文档包——概述、工作流、代码示例、API 参考，像写 README 一样。论文说这可能是错的：文档是写给人看的，模型需要的是指令。

他们做了 4,590 次对照实验，在 45 个科学计算场景上测试。结果很明确。

## 二、核心数据

| 模型看到什么 | 多少字 | 效果 |
|------|:--:|------|
| 完整 Skill 文档 | ~2,500 | **比什么都不给还差 1.1 个百分点** |
| 什么都不给 | 0 | 基线 |
| 紧凑的 Gene 指令 | ~230 | **比基线好 3.0 个百分点** |

更关键的是：**完整 Skill 让强模型 (Pro) 从 60.1% 掉到了 50.7%**——掉了将近 10 个百分点。越强的模型，被冗余文档拖累得越厉害。

### Skill 里到底什么有用

论文把 Skill 拆开测：

| Skill 里的部分 | 单独用的效果 |
|------|:--:|
| Overview（概述性描述） | **-4.7pp，明显有害** |
| Workflow（操作步骤） | +1.5pp，唯一有用的 |
| 错误处理 | +0.7pp |
| 陷阱提示 | +0.1pp |
| 完整 Skill 包 | -1.1pp |

大部分内容是噪音。真正有用的只有操作流程那一段。

### 不是"短就是好"

把 Skill 裁剪到和 Gene 一样短（~230 tokens），Gene 还是赢了（+3.0 vs +1.0）。说明不是字数的问题，是**组织形式**的问题。Gene 按"触发→策略→规避→验证"组织，Skill 按"概述→流程→示例→参考"组织。

### AVOID 比 DO 有效

论文测了不同的失败经验编码方式：
- 把失败和策略混在一起写：+2.0pp
- 只写策略：+2.5pp
- **只写失败警告**：+4.6pp

告诉模型"别做什么"的效果，是"要做什么"的近两倍。

### 结构本身就是价值

把同样的 Gene 内容展平成散文段落后，效果从 +3.0pp 掉到了 -0.5pp。结构化字段（keywords、summary、strategy、AVOID）本身就在帮模型理解信息。

### 真实进化效果

在 CritPt 物理研究基准上，用 Gene 驱动的进化系统（不改模型参数，只靠推理时经验积累）：
- Base Model A: 9.1% → 18.57%
- Base Model B: 17.7% → 27.14%
- Token 成本从 $100 降到不到 $1

## 三、论文提出的方法：GEP

论文配套了一套叫 GEP (Gene Evolution Protocol) 的协议：

```
三层对象:
  Gene    ← 原子控制单元，~230 tokens，注入模型
  Capsule ← 一次执行的全记录（策略用了哪个、结果怎样）
  Event   ← 不可变的进化日志

六阶段循环:
  Scan → Signal → Intent → Mutate → Validate → Solidify
  (扫描执行日志 → 识别失败 → 生成修复方案 → 执行验证 → 固化为新 Gene)
```

但这套协议依赖独立的 GEP Hub 和 Evolver 引擎，现有 agent 框架没有这些基础设施。

## 四、我们的验证实验

我们没用论文的合成场景，直接在真实生产 Skill（campus-repo-knowledge）上做实验。

### 怎么做的

同一个任务——给 Campus HR System 生成知识库——用三个条件跑：

- **无 Skill**：Agent 没有任何指导
- **改造前**：完整 SKILL.md（3,100 字，和现在生产环境一样）
- **改造后**：混合方案（~450 字，策略指令 + 结构规范）

三个 Agent 调用方式完全一样，唯一区别是注入的指令长度。

### 结果

| | 无 Skill | 改造前 (3,100 字) | 改造后 (~450 字) |
|------|:--:|:--:|:--:|
| 模块归并 | ❌ 建了技术层模块 | ✅ | ✅ |
| 结构规范 | ❌ 缺 module-map.json | ✅ | ✅ |
| 文档命名 | controller/service 后缀 | interface-{method}-{name} | 中文业务名 |
| 占位词 | 0 | 0 | 0 |
| 业务覆盖 | ✅ | ✅ | ✅ |

**改造前**最规范但每次注入 3,100 字太贵。**纯 Gene (280 字)** 丢了 module-map.json 和目录约定——太短也不行。**混合方案 (~450 字)** 刚好。

### 和论文不太一样的地方

论文测的是"代码能不能跑通"，我们测的是"知识库写得好不好"。论文用 Gemini，我们用 Claude。论文跑了 4,590 次，我们每个条件只跑了一次。但方向一致：紧凑的结构化指令比完整文档包更有效。

我们多发现了一点：**对于有严格结构要求的任务，纯 Gene 太短，需要加点结构规范。~450 字是最优区间。**

## 五、这意味着什么

### 对写 Skill 的启示

**把 SKILL.md 从操作手册变成执行卡片。** 控制在 500 字以内。完整文档放 `references/`。

具体做法：
1. 删掉概述、背景、代码示例、排错指南 → 移到 `references/FULL.md`
2. 保留场景路由、策略步骤、AVOID、目录规范、验证命令
3. 散文化段落改成结构化列表
4. 从失败经验里提炼 AVOID 条目（告诉模型别做什么，这比告诉它做什么更有用）

### 改造成本

**零架构改动。** 不建新文件类型，不引入新协议。Agent 框架照常只读 SKILL.md——只是内容变短了。这是这个方案最大的优势：现在就能用，不需要等任何框架更新。

### 不适合的情况

- 纯知识库 Skill（内容本身就是价值，压不了）
- SKILL.md 本来就不到 500 字（已经够短了）
- 一次性任务（不值得花时间提炼）

## 六、总结

1. **文档越长≠越好。** 论文数据：完整 Skill 拖慢强模型近 10pp。我们验证：3,100 字和 450 字产出质量相当。

2. **组织形式比字数重要。** 同样的内容，结构化列表比散文段落有效。AVOID（别做什么）比 DO（要做什么）有效近两倍。

3. **实用方案是把 SKILL.md 写短。** 控制在 500 字以内：场景路由 + 策略步骤 + AVOID + 结构规范。完整文档丢 references/。不改任何框架代码。

4. **不是越短越好。** 我们实验发现纯 Gene (280 字) 会丢结构约定。对于有严格格式要求的任务，~450 字的混合方案是甜点。
