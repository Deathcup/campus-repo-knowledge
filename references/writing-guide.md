# 面向人和 Agent 的编写指南

## 总体写法

每节先回答“它为什么存在、做什么、何时发生”，再列代码位置。第一次接触项目的人不应先理解框架目录才能理解业务。

优先写：

- “日志查询模块接收管理后台的组合筛选请求，校验租户权限后查询 Elasticsearch，并把结果转换为统一分页结构。”

避免只写：

- “包含 `EsLogController`、`EsLogServiceImpl`、`EsLogMapper`。”

代码标识、接口路径、配置键和命令保留原文，其余内容使用中文。短段落解释行为，表格承载重复字段，编号列表描述调用顺序。

采用“业务 → 流程 → 规则 → 实现 → 开发”的叙事顺序：

1. 先让读者知道谁为什么使用这个模块。
2. 再从触发到结果讲一遍完整流程。
3. 单独提炼决定行为的规则和边界。
4. 最后把每一步落到组件、服务、数据和代码证据。
5. 用开发指南告诉读者如何安全扩展，而不是只告诉他代码在哪里。

不要为了短而省略业务推理。渐进加载由目录层级解决，模块开发手册内部应优先完整。

## 总览摘要

根总览回答“项目由哪些部分组成、最重要的端到端业务旅程是什么、问题下一步去哪”。子系统总览回答“本子系统有哪些业务模块、它们怎样协作、典型业务旅程怎样经过它们、什么词能命中它”。

每条模块摘要采用：

```text
<模块名>：<业务职责>；入口/检索词：<接口路径、页面路由、公开符号、别名>；文档：<链接>
```

避免“工具类模块”“公共模块”“处理相关逻辑”等无法路由的模糊描述。

## 接口目录

同时记录外部接口和重要内部契约：HTTP、RPC、GraphQL、CLI、事件消费者/生产者、定时任务、公开库函数、页面路由或前端 API 客户端。

接口目录至少含：

| 字段 | 内容 |
| --- | --- |
| 方法与路径 / 调用入口 | 原始标识，如 `POST /eslog/query` |
| 用途 | 谁在什么场景调用 |
| 入口实现 | 相对路径和 Controller/Handler/函数 |
| 核心实现 | 相对路径和 Service/UseCase/Store/Composable |

接口详解进一步说明鉴权、参数默认值与校验、输出、错误、事务、缓存、分页、幂等和外部依赖。没有的机制明确写“不涉及”，不要留下泛化模板。

## 实现链路

用 3–8 个编号步骤描述正常路径，再单列关键分支。每一步包含行为和代码锚点：

```text
1. `src/.../EsLogController.java#query` 解析筛选条件并交给业务层。
2. `src/.../EsLogService.java#query` 注入租户范围、规范化时间区间。
3. `src/.../EsLogRepository.java#search` 组装 ES DSL 并执行查询。
4. `src/.../EsLogAssembler.java#toPage` 转换为统一分页响应。
```

对关键分支说明触发条件和可见结果，例如“无日志权限时在步骤 2 返回 `403`，不会访问 ES”。

链路中的每一步都应包含“行为 + 原因 + 证据”。以下写法不合格：

- “调用 `query()` 查询数据。”
- “Service 处理业务逻辑。”
- “使用 Pinia 管理状态。”

应改写为：

- “`query()` 先把未指定的结束时间补为当前时刻，并把开始时间限制在租户允许的保留周期内，避免跨租户或超范围扫描；随后才组装 ES 条件。”
- “页面 store 保留筛选条件而不保留结果列表，因此从详情页返回时筛选项仍在，但会重新请求最新结果。”

## 前端写法

从用户可见行为写起，再解释 View、组件、状态和 API 如何共同实现。组件表中的“职责”必须是业务职责，例如“管理筛选条件并在用户确认后触发查询”，不能只是“封装表单”。

组件树用来展示所有权和协作，不要求列出每个按钮或 UI 库组件。对重要组件说明：用户能力、父子契约、状态归属、触发的副作用以及生命周期行为。

页面流程不能停在“加载列表并调用接口”。至少写明初始化来源、默认筛选、加载/空/错状态、主要操作、成功反馈、失败保留什么状态、离开页面如何清理。

## 后端写法

按业务用例和规则组织正文。接口章节要把字段语义与完整实现关联起来，重点解释 Service/UseCase 内的条件、转换、查询和副作用。

对查询说明业务过滤如何转换为数据库/ES 条件；对写操作说明前后状态、事务边界和失败后结果；对事件和外部调用说明发生顺序、重试/补偿及其对用户结果的影响。

没有事务、幂等、缓存、竞态保护或重试时，不要省略该节，写清“不涉及”或“当前没有保护”的证据和风险。

## 开发指南写法

使用具体改动场景，例如“增加一种日志类型筛选”或“在详情弹窗增加重试动作”，逐步说明通常要修改的 View/组件/store/API 或入口/业务服务/模型/仓储/迁移/测试。列出必须保持的契约、常漏位置和最小验证方法。

通用建议如“遵守代码规范”“添加测试”“修改相关文件”没有知识价值，应替换为当前仓库的真实位置和约束。

## 人类可读性检查

- 首次出现的项目术语有中文解释或术语链接。
- 读者能知道模块“不负责什么”，避免错误修改位置。
- 参数说明包含业务语义，不只是类型。
- 数据字段说明包含单位、时区、枚举含义或生命周期。
- 测试写清怎么运行、覆盖什么和没覆盖什么。
- 排障从症状出发，指出日志、指标、配置和关键代码入口。
- 不粘贴大段源码；使用短伪代码、流程图或路径链接。
- 只读文档能讲清一条成功流程和一条失败流程，而不是必须再打开源码才能知道发生了什么。
- 前端能画出 View 和重要组件的关系，后端能列出关键业务规则和数据变化。
- 读者知道如何增加一个相邻能力，以及最容易漏改或破坏的位置。

## 事实、推断与未知

- 事实：由源码、测试、构建配置或运行证据确认，附相对路径。
- 推断：明确写“根据代码/提交推断”，附依据和置信度。
- 未知：写成可回答的问题，例如“生产环境 `ES_LOG_INDEX` 由哪个部署仓库注入？当前仓库只发现读取位置 `...`”，而不是只写“待补充”。

未知项也必须是调查后的结论：列出已经检查的源码、测试、配置或历史范围，说明当前仓库为什么不能给出更确定的答案，以及该未知会影响什么开发决策。禁止用占位句代替调查。

## 完稿清零规则

知识库交付前必须把每个模块放入独立目录，并对 `.repo-knowledge/` 下全部 Markdown 做残留扫描。`待补充`、`待调查`、`待核对`、`TODO`、`TBD`、模板变量和“稍后替换”类文字均视为未完成；发现后回到源码、测试、配置和历史继续取证。只有具体事实、带证据的推断，或写明“已检查范围 + 尚不可知原因 + 开发影响”的明确问题可以保留。

机械检查和新人上手抽查都通过才算完稿。不得通过删除深度章节、证据链接或失败分支来让检查通过。

## 更新纪律

接口或实现变化时先更新模块当前态；模块名、职责或检索词变化时更新子系统总览；子系统边界或跨系统链路变化时更新根总览。需求文档记录历史原因，不能代替当前态。
