# 模块深度调查与新人上手验收

本协议用于把“代码地图”升级为“开发手册”。调查时允许投入大量上下文；不要因为已经定位到文件或接口就停止。

## 通用取证顺序

1. 从用户、调用方或定时/事件触发者出发，写出模块存在的业务原因。
2. 找出所有入口，但只把入口当起点；沿调用链追到最终业务结果、数据变化和外部副作用。
3. 阅读关键条件判断、循环、映射、查询构造、状态转换和异常处理。对每个非机械逻辑回答“何时触发、做什么、为什么、结果是什么”。
4. 读测试以确认预期行为和边界；缺测试时明确风险，不把实现偶然行为包装成稳定契约。
5. 读历史需求和决策补充“为什么”，但以当前源码和测试描述“现在怎样”。
6. 把结论写成新人可阅读的业务叙事，再附路径和符号证据。不要按读取文件的顺序写调查日志。

## 前端模块调查

### 页面与入口

- 找出路由定义、菜单入口、父子路由、重定向、动态加载、守卫、权限指令和直接访问行为。
- 说明页面为哪类用户、哪项业务目标服务，以及进入页面前需要具备什么状态。
- 区分一个业务的列表、详情、编辑、弹窗和嵌套页面，说明它们如何衔接。

### View 和组件

完整阅读根 View 的 template/render、script/setup、生命周期和样式中影响行为的部分。沿 import 和模板使用追踪重要业务组件，直到能画出组件树并解释：

- 组件给用户提供什么能力；
- 为什么由该组件负责，而不是父组件或 store；
- 关键 props、emits、slots、provide/inject 或 context 契约；
- 哪些状态在组件本地、父 View、store 或 composable；
- 哪些组件触发 API、改变路由、打开弹窗或修改其他组件状态；
- 组件卸载、重开、切换记录或切换路由时如何重置。

不要罗列所有 UI 库组件。重点说明承载业务动作、复杂状态、复用契约或关键展示的组件，纯布局组件可归类简述。

### 用户流程与交互逻辑

至少重建：首屏初始化、核心成功路径、筛选/分页/排序、查看或编辑、提交、取消、空态、加载态、权限不足和请求失败。对每个业务动作追踪：

```text
用户操作 → 事件处理 → 表单/业务校验 → 状态变更 → API 请求 → 响应转换 → UI 反馈
```

检查并解释字段联动、显示/隐藏、禁用条件、防抖、请求取消、竞态处理、重复提交、乐观更新、回滚、缓存、URL 同步和错误提示。

### 状态和接口

- 为重要状态记录来源、所有者、更新时机、消费者和失效/持久化规则。
- 阅读 store/composable 的实现，不要只列 state/action 名。
- 阅读 API 调用点前后的参数构造、默认值、格式转换、DTO→ViewModel 映射和错误处理。
- 若前后端同仓，链接后端模块并核对字段、枚举、分页、时区、空值和错误码语义。

## 后端模块调查

### 业务用例

按“查询日志”“提交订单”“停用账号”等用户/系统目标组织，而不是按 Controller、Service、Repository 文件组织。对每个用例说明：触发者、前置状态、权限和数据范围、正常结果、数据变化、外部副作用、失败结果。

### 实现深挖

沿每个入口追踪到业务真正发生的位置，至少检查：

- 参数如何规范化、补默认值和交叉校验；
- 权限、租户、组织、所有权和数据范围如何注入查询或写入；
- 关键条件分支、状态机和禁止转换；
- 计算、聚合、匹配、排序、分页、去重和映射算法；
- SQL、ES DSL、ORM 条件、索引、批处理和性能假设；
- DTO、领域模型、实体和响应之间的转换及字段丢失/派生；
- 事务边界、锁、版本号、幂等键、缓存一致性和并发竞态；
- 消息、事件、第三方调用、审计、文件和通知的顺序与失败策略；
- 异常如何转换为错误码，哪些步骤发生后失败会留下部分结果；
- 日志、指标和 trace 如何支持生产排障，哪些敏感信息不能记录。

“Controller 调用 Service，Service 调用 Repository”不是实现说明。必须描述 Service 内部做了哪些业务判断和转换、Repository 查询表达了什么业务筛选。

### 数据与规则

- 解释模型和字段的业务语义、单位、时区、枚举、唯一性、生命周期和关联。
- 每条重要规则记录触发条件、系统行为、业务原因、代码和测试证据。
- 区分已确认业务规则、框架约定、当前实现限制和合理推断。

## 开发指南调查

模块手册必须回答“我要在这个业务上加代码，具体从哪开始”：

- 增加同类页面、动作、接口、字段或状态通常修改哪些位置；
- 哪些契约必须同步，哪些代码由工具生成不能手改；
- 哪些权限、数据迁移、缓存、事件、配置和兼容性容易遗漏；
- 最小启动、测试数据准备、验证命令和关键测试是什么；
- 常见失败症状从哪里排查。

开发指南必须针对当前仓库，不能写“修改相关 Service 并添加测试”这类通用建议。

## 新人上手验收问题

不打开源码，只读模块手册，要求另一位读者回答：

1. 这个业务服务谁，解决什么问题，不负责什么？
2. 从用户/调用方触发到结果可见，完整流程是什么？至少说出一个失败流程。
3. 最重要的 3–8 条业务规则是什么，各自在什么条件下生效？
4. 前端：根 View 如何编排，重要组件分别负责什么，状态和 API 如何流动？
5. 后端：核心用例在哪实现，关键判断/查询/计算、数据变化和副作用是什么？
6. 权限、异常、事务/竞态或前端异步竞态如何处理？
7. 要增加一个相邻能力，需要修改哪些文件类别、保持哪些契约、补哪些测试？
8. 如何在本地跑起来并验证，失败时先看哪里？

任一问题只能回答文件名、类名、路由或接口字段，视为未通过。回到源码继续调查并补写。
